# ML pipelines

> All data is synthetic and generated by `ml/generate_data.py`. The models learn the **demonstration criteria** written in that file, plus injected noise. Their metrics say how well they reproduce those invented rules, not anything about real creditworthiness or real scheme eligibility. The model output is advisory; an officer always decides.

## Files

| File | Role |
|---|---|
| `ml/generate_data.py` | Generates 6,000 synthetic applicants per route, then deliberately adds 120 duplicate rows, misspelled and unknown state names, missing values, invalid values and label noise |
| `ml/common.py` | Shared helpers: Indian state normalisation (same alias table as `lib/domain/states.ts`), one-hot encoding, JSON export |
| `ml/pipelines.py` | The two training pipelines |
| `ml/train_all.py` | Runs data generation and both pipelines (`npm run ml:train`) |
| `ml/tests/` | 18 pytest cases: state normalisation (parametrised), exported JSON matches the joblib model, clean data has no duplicates or missing values, each model beats the majority baseline |
| `ml/reports/*.md`, `*_metrics.json` | Generated reports |
| `ml/artifacts/*_model.json` | Exported trees used by the app; `*_parity.json` fixtures for the TypeScript parity test |

## Pipeline stages (both routes)

1. **Ingestion** of the raw CSV.
2. **Validation and cleaning**: exact duplicates removed; state names normalised to codes, and rows with unrecognised states are dropped rather than guessed; invalid rows (negative income, age under 14, non-positive amount or tenure) dropped. Counts are logged.
3. **Feature-level de-duplication** so the same applicant cannot appear in both train and test.
4. **Stratified 80/20 split** (fixed seed `20261124`, so retraining is reproducible).
5. **Missing values**: median (numeric) or mode (categorical) learned from the **training split only**, to avoid leakage.
6. **Feature preparation**: one-hot encoding with fixed category lists. The bank route adds three engineered ratios (repayment burden, loan-to-income, collateral coverage), computed identically in `server/ml/features.ts`.
7. **Training**: `GridSearchCV` with 5-fold stratified CV over `max_depth` and `min_samples_leaf`, F1 scoring, `class_weight="balanced"`.
8. **Evaluation** on the held-out test set against a majority-class baseline.
9. **Serialisation** with joblib (`*_model.joblib`, for Python reuse) and **JSON export** of the tree structure for in-app inference.
10. **Parity fixtures**: 200 held-out rows with the Python probabilities; `tests/unit/ml.test.ts` checks that the TypeScript inference matches them to 9 decimal places.

## Government route: Decision Tree

Features: age, land cultivated, yearly farm income, amount requested, bank account (yes/no), earlier scheme default (yes/no), farmer category, crop type, water source, support purpose.

Demonstration criteria: age 18–70, land ≤ 5 acres, farm income ≤ ₹2,50,000, request ≤ ₹1,00,000, has a bank account, no unmet earlier scheme conditions; 5% label noise.

| Model | Accuracy | Precision | Recall | F1 | ROC AUC | CV F1 |
|---|---|---|---|---|---|---|
| Majority-class baseline | 0.708 | 0.000 | 0.000 | 0.000 | 0.500 | — |
| **Decision tree** (`gov-dt-10b2305db4`) | 0.936 | 0.910 | 0.867 | 0.888 | 0.912 | 0.910 |

Held-out confusion matrix: TN 788, FP 29, FN 45, TP 292 (1,154 rows).

## Bank route: Decision Tree compared with Random Forest

Features: age, yearly income, existing monthly repayments, amount, tenure, years farming, land, collateral value, credit history, loan purpose, collateral type, plus the three engineered ratios.

Demonstration criteria: age 21–65, repayments ≤ 50% of monthly income, loan ≤ 3× yearly income, at least 2 years farming, no poor credit history (fair history approved 75% of the time), collateral covering the loan above ₹1,60,000; 4% label noise.

| Model | Accuracy | Precision | Recall | F1 | ROC AUC | CV F1 |
|---|---|---|---|---|---|---|
| Majority-class baseline | 0.699 | 0.000 | 0.000 | 0.000 | 0.500 | — |
| **Decision tree** (`bank-dt-552465725c`) | 0.923 | 0.861 | 0.888 | 0.874 | 0.919 | 0.893 |
| Random forest (60 trees) | 0.912 | 0.824 | 0.899 | 0.860 | 0.922 | 0.872 |

The decision tree was selected because it had the higher cross-validated F1 on the training split. The random forest has slightly higher ROC AUC and recall, but the difference is small and the single tree gives a decision path an officer can follow. The selection rule is fixed in code (highest CV F1), not chosen after looking at test results.

## In-app assessment

`server/ml/assess.ts` combines three things:

1. **Model probability** from the exported tree.
2. **Rule checks** from a versioned config (`lib/data/rules/*_rules_v1.json`): HARD rules (the demonstration criteria) and SOFT rules (recommended documents).
3. **Outcome policy**:
   - any HARD rule failed: `NOT_ELIGIBLE`, or `NEEDS_REVIEW` if the probability is still ≥ 0.5;
   - no failures and probability ≥ 0.6: `ELIGIBLE`;
   - only SOFT failures and probability ≥ 0.6: `NEEDS_REVIEW` (ask for the documents);
   - otherwise `NEEDS_REVIEW`.

Explanations shown to officers:

- **Contributions** (Saabas path method): how much each feature moved the probability along the path from the root to the leaf. The root value is the "model starting point". Because training used balanced class weights, this starting point is about 50% and is **not** a real approval rate.
- **Decision path**: the actual splits taken, written in plain language (for example "Land you cultivate is 2 (at or below 5.01)").
- **Failed conditions and suggestions**: for example, the largest loan that would keep repayments under half of monthly income.

Farmers see the outcome, the failed conditions ("What needs attention") and the suggestions. The model estimate and contributions are available to them in a collapsed section; the starting point and the decision path are shown to officers only.

Each assessment stores the model version, the rule config version and the application revision. A resubmission marks earlier assessments as stale, and approval is blocked until a current assessment exists.

## Limitations

- Synthetic labels follow simple threshold rules, so a tree can learn them almost perfectly. High scores here do not transfer to real data.
- No fairness analysis was possible: the synthetic data has no protected attributes by design, and real-world bias cannot be measured on invented data.
- Probabilities are not calibrated.
- The state feature is not used by the models; it is only validated.
